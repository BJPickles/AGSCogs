# AGS Activity — Deep Code Audit (2026-11-11)

**Repository:** [BJPickles/AGSCogs](https://github.com/BJPickles/AGSCogs)  
**Scope:** `agsactivity/agsactivities.py` (1,616 lines), `agsactivity/__init__.py`, `agsactivity/info.json`, AGS Activity tests/workflows and repository rolling audit.  
**Audited commit:** [`a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5`](https://github.com/BJPickles/AGSCogs/commit/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5).  
**Method:** Read-only static source review of commands, permissions, interaction callbacks, Config state transitions, scheduling/restart recovery, embeds/DM sends, lifecycle, retention/metadata and existing tests. Cross-checked discord.py interaction behavior and Red user-data deletion API against official documentation.  
**Not performed:** Live Red bot installation, Discord API invocation, concurrent runtime simulation, user-data deletion test, code modification, or new automated tests. Production consequences require staging confirmation. The old isolated task (nine tests) and pagination (11 tests) suites were reported passing in earlier PRs; they were **not re-run** as part of this review.

**Executive assessment:** The cog supports a wide feature set but is **not ready for unrestricted deployment** until the first group of findings is addressed. In particular, cross-guild instance lookup, non-atomic updates, unbounded member-triggered mass DMs, private accept validation, destination modal handling and broken public extension require focused fixes. AUD-011 (task cancellation/ownership) and AUD-012 (activity-list pagination) are fixed in source but still need live Red/Discord verification; they are **not reopened** by this report.

## Detailed findings

### AUD-018 — High — Ambiguous activity IDs permit cross-guild state changes

**Evidence:** [source lines 81–86](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L81-L86), [source lines 1251–1255](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1251-L1255), [source lines 1311–1320](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1311-L1320), [source lines 1464–1465](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1464-L1465), [source lines 1528–1551](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1528-L1551), [source lines 1579–1606](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1579-L1606), [source lines 726–736](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L726-L736).

**Finding / impact:** IDs are sampled from only 40 adjectives × 40 nouns (1,600 combinations), with uniqueness enforced only within the creating guild. DM callbacks and destination updates search all bot guilds for the first matching ID. Two guilds can legitimately have the same ID, so an interaction in one guild can read or mutate the other's activity, or send a reply to the wrong owner.

**Recommended correction and regression coverage:** Persist a globally unique, unambiguous activity key (guild ID + activity ID, or UUID) in each custom_id and look up exactly that guild. Migrate existing DM views carefully; detect and disambiguate old collisions instead of silently resolving the first match. Test two guilds with the same ID and the same invited user.

### AUD-019 — High — Concurrent interactions can lose participants and other changes

**Evidence:** [source lines 1400–1425](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1400-L1425), [source lines 1438–1450](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1438-L1450), [source lines 1464–1485](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1464-L1485), [source lines 1528–1557](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1528-L1557), [source lines 386–440](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L386-L440).

**Finding / impact:** Each button handler independently reads the entire instances dictionary, mutates it, and replaces it with .set(insts), with no per-activity or per-guild lock/transaction. Two near-simultaneous joins (or a join and a leave, RSVP, start, stop or timer) can both acknowledge success but the last write discards the other mutation. Capacity checks also operate on stale participant counts.

**Recommended correction and regression coverage:** Protect state transitions with scoped asyncio locks plus re-reads and revalidation, or atomic Config context managers where supported; avoid replacing the entire guild instances mapping for one activity. Include high-contention join/leave, slot limit and start/end race tests.

### AUD-020 — High — Ordinary members can trigger mass unsolicited DMs

**Evidence:** [source lines 1139–1145](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1139-L1145), [source lines 1206–1221](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1206-L1221), [source lines 1279–1299](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1279-L1299), [source lines 777–835](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L777-L835).

**Finding / impact:** The `activity start` command has no explicit staff check, and the private-activity wizard accepts `all` or an entire role. Any member allowed to invoke this command can cause the bot to DM a large number of guild members, repeatedly. This risks spam, rate limits, complaints and service disruption. Whether community-wide starts should be open is a product decision, but unrestricted mass-DM is not a safe default.

**Recommended correction and regression coverage:** Restrict mass target selection to trusted roles/guild owners or require approval; add explicit recipient caps, per-author creation cooldowns, deduplication, batching and opt-out. Keep individual invited-friend activities available if desired. Test unauthorized mass-target attempts.

### AUD-021 — High — Destination edit flow raises after acknowledging and cannot edit DM embeds

**Evidence:** [source lines 645–662](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L645-L662), [source lines 726–772](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L726-L772).

**Finding / impact:** The destination modal first calls `modal_interaction.response.send_message`, then `_handle_destination_update` later calls `interaction.response.edit_message` on the same interaction: Discord interactions may be responded to only once, yielding `InteractionResponded`. The DM update loop also calls `dm.edit_message(mid, embed=e)`, which is not a DMChannel method in discord.py; exceptions are silently swallowed, leaving invite/reminder/manage embeds stale. The public embed may update before the final exception.

**Recommended correction and regression coverage:** Use defer/followup or one initial response and later followup/edit_original_response. For DMs use `msg = await dm.fetch_message(mid); await msg.edit(embed=e)`. Report partial failures and test modal → persistence → public and DM updates.

### AUD-022 — High — Private invitation actions bypass slot, state and recipient checks

**Evidence:** [source lines 1414–1425](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1414-L1425), [source lines 1475–1485](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1475-L1485), [source lines 1528–1577](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1528-L1577), [source lines 1590–1613](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1590-L1613).

**Finding / impact:** Unlike public/private manage joins, `_handle_invite_accept` has no slot cap, OPEN/private check, target ownership check or invite-membership check, allowing all outstanding invitees to accept beyond max_slots and stale interactions to mutate ended events. RSVP/reminder handlers likewise never verify interaction.user.id == target_id or the activity status. Extend/finalize handlers do not check the clicking user is owner; delivery via owner DM limits ordinary reachability but is not a substitute for server-side authorization.

**Recommended correction and regression coverage:** Centralize authorized transition checks for each button, validate target guild/owner/status/capacity against freshly loaded state and reject stale/unauthorized interactions. Reuse the lock from AUD-019. Test capacity full, wrong user, wrong status and old messages.

### AUD-023 — Medium — Private activity details are discoverable through unrestricted guild commands

**Evidence:** [source lines 884–935](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L884-L935), [source lines 478–529](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L478-L529).

**Finding / impact:** `activity list` includes every private activity ID/title/owner/status, and `activity info` shows participant display names, destination and schedule to any guild member who can invoke the command. This conflicts with the ordinary expectation of private invitation-only events and exposes attendance information.

**Recommended correction and regression coverage:** Define privacy semantics explicitly. Hide private events from non-invitees or limit details to the creator, invited members and staff; provide a redacted public summary only if desired. Test non-invitees, invitees and moderators.

### AUD-024 — High — Extending an auto-ended public event does not restore participation controls

**Evidence:** [source lines 564–579](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L564-L579), [source lines 581–597](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L581-L597), [source lines 1590–1599](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1590-L1599).

**Finding / impact:** Auto-end edits the public message with `view=None`; `_handle_extend` changes Config status back to OPEN and schedules another deadline but never edits the public message or reattaches `PublicActivityView`. An extended public activity therefore remains non-joinable/non-leavable from its advertised message. The display is also stale, and the extension does not notify attendees.

**Recommended correction and regression coverage:** On extension, restore the correct public embed and persistent view, register it with the message ID, and refresh private activity views as appropriate. Test auto-end→extend→join/leave→re-end, including restart between stages.

### AUD-025 — Medium — Several live interactive controls are not restored after restart

**Evidence:** [source lines 386–440](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L386-L440), [source lines 623–674](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L623-L674), [source lines 701–718](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L701-L718).

**Finding / impact:** Startup reconstructs public, live private invite/manage, scheduled RSVP and extend views, but omits scheduled-private reminder Leave views. The temporary destination Update/Skip view is neither persisted nor re-registered. These buttons on previously sent messages can stop responding after a bot restart or reload.

**Recommended correction and regression coverage:** Persist and restore all applicable message IDs/views (or convert destination updates to commands); track view lifecycle on unload. Add real interaction recovery tests for every view type across a clean restart.

### AUD-026 — Medium — Failed posting can strand activities as OPEN without a usable message

**Evidence:** [source lines 1251–1274](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1251-L1274), [source lines 777–799](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L777-L799), [source lines 606–621](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L606-L621), [source lines 676–690](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L676-L690), [source lines 386–440](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L386-L440).

**Finding / impact:** Activity state is saved before Discord delivery. Scheduled starts transition to OPEN before posting; on a failed public send, the exception is logged but no retry or rollback is scheduled. Immediate starts can retain a stored OPEN entry when the configured channel is invalid or posting fails. Startup only restores public views for known message IDs and never retries missing posts.

**Recommended correction and regression coverage:** Use a publishing/launch state or a recoverable outbox, post idempotently with bounded retries and save message IDs after success. Provide owner-visible error/retry paths and tests for Forbidden, NotFound, transient failure and restart recovery.

### AUD-027 — Medium — Embed and message size limits are not enforced outside the list command

**Evidence:** [source lines 478–529](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L478-L529), [source lines 1019–1026](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1019-L1026), [source lines 1112–1122](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1112-L1122), [source lines 1174–1181](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1174-L1181), [source lines 1323–1351](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1323-L1351), [source lines 454–473](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L454-L473).

**Finding / impact:** AUD-012 constrains only activity-list pages. `_build_embed` puts the entire participant roster into a single 1,024-character field and allows arbitrarily long destination values; busy activities can fail Discord embed validation. Template listing and monthly prune summaries are assembled into single messages without Discord's 2,000-character message cap. These failures can leave stale views or omit summaries.

**Recommended correction and regression coverage:** Bound and paginate participant lists, validate destination lengths, cap total embed characters, and chunk templates/prune summaries. Test with 30–100 participants, long names/destinations and hundreds of templates/pruned records.

### AUD-028 — Medium — User-data deletion integration and disclosure are incomplete

**Evidence:** [source lines 91–97](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L91-L97), [source lines 1251–1269](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1251-L1269), [source lines 1290–1297](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1290-L1297), [source lines 1311–1320](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1311-L1320).

**Finding / impact:** The cog stores owner IDs, participant IDs, DM target IDs, invitation/RSVP choices, timestamps and DM message IDs. No `red_delete_data_for_user` implementation exists in the Activities class, so Red's user-erasure pathway is not handled by this cog. `info.json` says only activity definitions/instance state are stored and omits these practical details. Historical messages and operational records need an explicit retention/deletion policy.

**Recommended correction and regression coverage:** Implement and test the Red data-deletion hook for supported requester types; remove or anonymize references and stop/retarget associated message views where applicable. Expand `end_user_data_statement` with actual stored user data and retention. Preserve necessary moderation records only under a documented exception.

### AUD-029 — Medium — Unbounded DM refresh fan-out can overwhelm Discord and background workers

**Evidence:** [source lines 1323–1351](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1323-L1351), [source lines 1500–1502](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1500-L1502), [source lines 1524–1525](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1524-L1525), [source lines 1570–1571](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1570-L1571).

**Finding / impact:** Each private join/leave/accept spawns a new task to edit *every* invitation, reminder and manage message sequentially. With many invitees this can create overlapping O(events × recipients) requests and task bursts during simultaneous responses. No coalescing or concurrency limiter exists. A 429 retry path also refers to `msg` before assignment if fetching failed.

**Recommended correction and regression coverage:** Coalesce refreshes per activity and edit only necessary messages or apply bounded batches/concurrency with cancellation and retry handling. Benchmark with many invitees and concurrent responses; inspect real rate-limit behavior.

### AUD-030 — Medium — Scheduled-owner and auto-end notification lifecycle is inconsistent

**Evidence:** [source lines 581–600](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L581-L600), [source lines 693–724](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L693-L724), [source lines 782–786](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L782-L786), [source lines 454–460](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L454-L460).

**Finding / impact:** Immediate activities auto-add their creator, but scheduled public activities and scheduled private events do not automatically add the owner. Auto-end retrieves its owner with `get_user` only (not `fetch_user`), silently skipping the Extend/Finalize DM when the owner is not cached; the activity becomes ENDED with no fallback extension command. The monthly prune also removes all ENDED activities, including auto-ended ones awaiting the owner's decision.

**Recommended correction and regression coverage:** Standardize owner participation and explicitly decide whether owners use a slot. Fetch absent owner users where possible, provide an owner command to extend/finalize, and separate awaiting-finalization from final ENDED/prunable state. Add scheduled→auto-end→month-boundary tests.

### AUD-031 — Low — Installer guidance and wizard validation are outdated or incomplete

**Evidence:** [source lines 1004–1096](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1004-L1096), [source lines 1155–1250](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1155-L1250), [source lines 1068–1077](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1068-L1077), [source lines 1223–1232](https://github.com/BJPickles/AGSCogs/blob/a6e9a224cdbc2f31970bc8bd40d5c830a1f7bfc5/agsactivity/agsactivities.py#L1223-L1232).

**Finding / impact:** `info.json` tells installers to run a nonexistent `[p]activitytype` command and describes voice-call checks not implemented in this module. The start wizard does not catch `asyncio.TimeoutError` (unlike template save) and accepts `max_slots=0` as valid, making a full activity from the outset. Duplicate setup functions in the package and module add maintenance confusion.

**Recommended correction and regression coverage:** Correct installer text and feature claims, handle wizard timeout/cancellation cleanly, validate max_slots >=1 and document owner participation. Keep only the actual cog loader entry point.

## Staging validation matrix (suggested)

- **Multi-guild isolation:** In two guilds create the same `iid`; click a private invite, RSVP, manage, extend and destination control from each guild and verify that only its own state changes.
- **Contention:** Trigger 20 simultaneous joins for a 5-slot event; exactly five should succeed and all five should persist. Interleave a stop, leave and RSVP with a join.
- **Permission abuse:** Have an ordinary member attempt `all` and role-wide invitations; verify the policy, cap/cooldown, and opt-out enforcement.
- **Invite validity:** Attempt stale, full, expired, finalized and wrong-recipient component actions; verify no persisted mutations.
- **Restart/reload:** Exercise every view type before and after clean restart, including scheduled-private reminder Leave and destination Update/Skip.
- **Delivery failures:** Remove Send Messages, block DMs, make destination channel invalid, and restart the bot; verify retry/rollback and owner-visible diagnostics.
- **Extension:** Public activity auto-ends, owner extends, new member joins, another leaves, and event ends again; verify buttons and embeds throughout.
- **Bounds:** 100 participants with maximal display names, 2,000-character destination input, many templates, and many monthly-pruned records.
- **Privacy:** Request user deletion via Red's user-data API, verify no orphaned identifiers or buttons, and document records that must persist by policy.

## Limitations / future PR discipline

This report is a **static code audit**, not proof of successful runtime reproduction. Confirm each remediation with isolated regression tests and a staged Red/Discord integration pass. Every fix PR must update the permanent [AUDIT_HISTORY.md](../AUDIT_HISTORY.md), link back to its audit ID, retain historic entries, state what was tested and not tested, and note residual risks. Do not mark findings fixed merely because a code patch was written or a mock test passed.
